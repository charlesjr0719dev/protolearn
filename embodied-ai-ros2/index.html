Section 01

為什麼機器人需要語言模型

學習重點

Embodied AI 的核心問題是「翻譯」——把模糊的人類意圖變成精確的機器人動作。

傳統機器人靠腳本運作：If A then B。寫好的程式決定一切。這在工廠產線上沒問題——環境固定、任務重複、不需要理解。

但一旦環境變了、任務變了、或者你想用自然語言下指令，腳本就撞牆。「把綠色積木撿起來放到黑色架子上」——這句話對人類很直覺，但對傳統機器人來說，每個詞都是未定義的。

大型語言模型改變了這件事。LLM 能理解自然語言的意圖，把模糊的指令拆解成具體的子任務。但 LLM 本身只是一個會說話的大腦——它沒有手、沒有腳、看不見環境。

Embodied AI（具身智慧）就是在解決這個問題：給大腦一個身體。技術上的核心挑戰是翻譯——怎麼把 LLM 理解到的意圖，轉換成 ROS 2 節點能執行的精確動作。

如果你做過 AMR 專案，你已經碰過類似的翻譯問題：介面契約定義了「誰跟誰講什麼話、格式長怎樣」。Embodied AI 的翻譯問題是同一件事的上一層——不是系統之間的格式翻譯，而是人類語言到系統格式的翻譯。

來源
  • 概念定義：跨多個學術調查論文的共識（Intelligent Computing 2024、Wiley 2025、arXiv 多篇 2025-2026 survey）
  • AMR 介面契約對照：實測驗證經驗

Section 02

三種架構模式

學習重點

目前 LLM 連接 ROS 2 有三種主要模式，各自的取捨不同。不存在「最好的」，只有「適合場景的」。

模式 A：直接程式碼生成

LLM 收到自然語言指令後，直接寫出可執行的 Python 程式碼來控制機器人。

舉例：你說「往前走一公尺」，LLM 生成：

msg = Twist()
msg.linear.x = 0.2
publisher.publish(msg)
time.sleep(5)

這是 2026 年 Nature Machine Intelligence 論文（Mower 等人，華為 Noah's Ark Lab / TU Darmstadt / ETH Zurich）描述的兩種執行模式之一。

優點：彈性最高。LLM 可以處理全新的、沒預設過的任務。

風險：任意程式碼執行。LLM 生成的程式碼可能有 bug，在實體機器人上跑有 bug 的程式碼可能撞壞東西。

模式 B：結構化動作翻譯

LLM 不寫程式碼，而是輸出結構化的 JSON，描述要做什麼動作。一個專門的驗證節點檢查 JSON 格式正確後，才轉發給 ROS 2 執行。

一篇 2025 年發表在 PMC 的論文實測了這個方法：14 個 LLM 模型對 ROS 2 Nav2 導航堆疊下指令。LLM 輸出固定格式：

{
  "intent": "navigate",
  "goal_x": 2.5,
  "goal_y": 1.0,
  "note": "移動到桌子旁邊"
}

ROS 2 節點驗證 JSON 格式，不合格就自動重試（最多三次），合格就送進 Nav2 規劃器。

優點：可預測、可驗證。動作空間是封閉的，不會出現意外的程式碼。

限制：只能做你預先定義好的動作類型。LLM 沒辦法即興創造新動作。

AgenticROS（GitHub 148 星）把這個概念推得更遠：機器人透過「能力宣告」（Capability Manifest）告訴 LLM 自己能做什麼——drive_base、take_snapshot、find_object 等。LLM 針對這些動詞規劃，不碰底層的 ROS 2 topic。

模式 C：行為樹生成

LLM 把任務拆解成行為樹（Behavior Tree）結構——一組有順序、有條件分支、有備案的動作序列。同樣來自 Nature Machine Intelligence 論文的第二種執行模式。

舉例：「撿起綠色積木放到黑色架子上」被拆成：

  1. 找到綠色積木（找不到 → 旋轉掃描 → 再找）
  2. 移動到積木前方
  3. 計算抓取角度
  4. 抓取
  5. 移動到黑色架子
  6. 放下

優點：處理複雜多步驟任務最好，有條件分支和備案。

限制：行為樹本身就很難設計，LLM 生成的行為樹品質不一定穩定。

三種模式比較

A：程式碼生成B：結構化 JSONC：行為樹
彈性最高受限於預定義動作高（多步驟 + 分支）
安全性最低最高中等
複雜任務看 LLM 能力需要外部編排內建支援
驗證難度很難（任意程式碼）很容易（schema 檢查）中等
適合場景研究、原型生產環境、明確任務複雜自主任務

Section 03

安全層——為什麼 LLM 不能直接控制機器人

學習重點

理解為什麼需要在 LLM 和實體硬體之間加一道安全閘門，以及這道閘門怎麼運作。

ROSClaw（GitHub 196 星，MIT 授權）提出了一個核心原則：

「模型的輸出不應該直接控制機器人。」

為什麼？因為 LLM 會幻覺。它可能自信滿滿地生成一個會讓手臂撞到桌面的動作指令。在聊天視窗裡，幻覺只是一段錯誤的文字；在實體機器人上，幻覺可能是一個撞壞感測器的指令。

ROSClaw 的做法是在 LLM 和機器人之間放一個守門員（rosclawd）：

LLM 意圖 → 能力匹配 → 安全策略檢查 → 資源租借
→ 沙箱預演 → 派遣執行 → 感測器觀察 → 驗證 → 回執

沙箱預演

在 MuJoCo 物理模擬器裡先跑一次。如果模擬中手臂撞到東西，就不會送到真實硬體。

許可證制度

每次動作都需要一張有時效的許可證。過期就作廢。不存在「一次授權、永久執行」。

證據回執

每次動作完成後，系統產出一份帶時間戳的證據文件。不是「我做了」，而是「我做了、這是證據、這是感測器看到的結果」。

五個執行層級

層級說明用途
FIXTURE純合成資料單元測試
DRY_RUN只檢查格式和靜態策略部署前驗證
SIMULATION物理模擬（MuJoCo / Gazebo）安全驗證
SHADOW契約已定義，尚待驗收準備上線
REAL真實硬體，失敗就關正式執行

如果你做過 AMR，這個概念你不陌生——你的「翻譯員」就是在 MoveIt 和控制器之間做格式轉換和驗證的中間層。ROSClaw 把這個思路推到了 LLM 層級：不只翻譯格式，還要驗證意圖。

Section 04

延遲與模型選擇

學習重點

不同 LLM 的回應速度差異極大，選模型要看任務對延遲的容忍度。

PMC 論文實測了 14 個模型對 ROS 2 Nav2 下導航指令的延遲：

模型平均延遲特性
GPT-3.50.97 秒最快，變異度低
LLaMA-3.3-70B1.82 秒本地可部署（via Groq）
Claude 3.7 Sonnet2.71 秒中等
Gemini 2.5 Pro9.85 秒推理強但慢
GPT-512.14 秒最強推理但最慢

14 個模型的指令解析成功率都在 95-100%。差異在延遲和推理能力。

取捨：速度 vs 推理

即時控制（機器人在移動中需要持續決策）→ 用輕量模型（GPT-3.5 等級），低於 2 秒。

任務規劃（一次性拆解複雜指令，不需要即時）→ 用重量模型（GPT-5、Gemini 2.5 Pro），可以等 10 秒以上。

雲端 vs 本地部署

AgenticROS 支援 Ollama 整合（推薦 Qwen3-VL 8B/2B），零雲端 API 依賴。這對兩種場景很關鍵：

  • 隱私敏感：不想把機器人看到的畫面傳到雲端
  • 網路不穩：Wi-Fi 斷了機器人不能變笨

代價是本地模型的推理能力通常不如雲端大模型。

來源
  • 延遲數據：PMC/NIH 論文（2025），同行審查
  • Ollama 整合：AgenticROS GitHub repo——社群驗證
  • Qwen3-VL 推薦：AgenticROS README——廠商建議，未獨立驗證

Section 05

現在的工具生態

學習重點

了解目前可用的三個主要框架，知道它們各自的定位和成熟度。

ROS-LLM（學術框架）

Nature Machine Intelligence 論文（2026）的開源實作。來自華為 Noah's Ark Lab、TU Darmstadt、ETH Zurich。

定位：研究用框架。證明了「LLM + ROS = 可行」。適合想理解原理、跑學術實驗；不適合直接拿去做產品。

AgenticROS（AI 不可知介面層）

GitHub 148 星，Apache-2.0。不綁定特定 LLM——同一個機器人可以同時被 Claude、Codex、Gemini 控制，不用改程式碼。透過 MCP 連接。

核心概念是「能力宣告」：機器人告訴 AI 自己能做什麼，AI 針對動詞規劃，不碰底層 topic。支援 TurtleBot3 模擬、多機器人隊列、技能市集。

定位：快速讓 AI 控制 ROS 2 機器人。一行安裝（npx agenticros）。

ROSClaw（安全優先執行運行時）

GitHub 196 星，MIT，Alpha 階段。不是 ROS 2 的替代品，而是 AI 和 ROS 2 之間的中介軟體。核心訴求：「request 不等於 execution，execution 需要 evidence」。

UR5e 手臂模擬已通過，真實硬體驗證待完成。

定位：需要安全邊界和審計軌跡的場景。上手門檻最高。

Section 06

跟你的專案怎麼接

學習重點

把前五節學到的東西對應到你手上的兩個專案，看哪些概念可以直接用。

LanderPi

你的 LanderPi 已經有完整的 ROS 2 堆疊、6-DOF 手臂、LiDAR、Aurora930 Pro 深度相機。AMR 專案讓你理解了 ROS 2 的架構和介面契約。缺的是 LLM 層。

加上去的最快路徑：

  1. 先把 LanderPi 跑起來（組裝、開機、走一遍官方教學）——這步跟 LLM 無關
  2. 官方教學走完後，試 AgenticROS（一行安裝，支援 Pi 5）
  3. 透過 MCP 連接到 LanderPi 的 ROS 2 節點
  4. 用自然語言控制基本動作（前進、轉彎、拍照）

要注意：Pi 5 的算力跑本地 LLM 很吃力。比較實際的做法是 Pi 5 跑 ROS 2 和感測器，LLM 推理放你的 Mac Mini 或雲端。

最可能的接法：

Mac Mini（Claude / GPT）→ rosbridge WebSocket → Pi 5 Docker 裡的 ROS 2 → Hiwonder 舵機控制鏈

AI Little Monster

你的三層架構——Mac Mini 腦 / 手機感官 / 娃娃身體——本質上就是一個 Embodied AI 系統。差異在於 AI Little Monster 不需要 ROS 2（不是精密運動控制），但「意圖 → 拆解 → 執行 → 回饋」的迴圈是完全一樣的。

可以直接帶過去的概念：

  • 結構化動作翻譯（模式 B）：定義娃娃能做的動作清單，LLM 從清單裡選
  • 安全層的思路：LLM 幻覺在對話夥伴上的風險不是物理碰撞，而是說出不該說的話
  • 能力宣告：讓 LLM 知道娃娃「能做什麼」而不是「怎麼做」
來源
  • LanderPi 硬體規格：LanderPi 專案資料——你自己的文件
  • AgenticROS Pi 5 支援：GitHub README——社群驗證
  • rosbridge + Docker ROS 2 相容性：架構推論——未經實測驗證
